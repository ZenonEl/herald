# Herald Setup

Use Herald's CLI to resolve, preview and apply configuration changes. Find the installed root from this skill's `SKILL.md` path (`../..`), or use the checkout containing this skill when developing it. Run `uv run --isolated --locked --directory <root> herald <command>`. Use that same root and explicit config path throughout the operation. An isolated run keeps the listener's Python environment untouched.

1. Resolve the config used by the intended Herald instance. Prefer the user's explicit path or the active `HERALD_CONFIG`, otherwise use `~/.config/herald/config.toml`. Resolve any relative path in its intended working directory before passing it as `--config`. Ask if multiple configurations fit. Collect only the missing project, destination or change. Never guess a chat or topic ID.
2. **First setup:** If the config is absent and the user wants to create it, use `init --config <path> --project <key> --chat-id=<id>` with optional `--topic-id` and `--label`. Run `--dry-run --json` first. Reuse a supplied token file with `--token-file`. If the user has given the bot token in chat, use `--token-stdin` and a tool that passes it directly on stdin without echoing it. Keep it out of shell command text, arguments, output, and repository files. If direct stdin is unavailable, offer the token file or the CLI's hidden prompt. Use a local config location outside tracked project files. `init` creates one project and route and refuses to overwrite a config.
3. **Existing config:** Start with `update --config <path> --project <key>` and add only the requested fields: `--route` to select an existing route, `--chat-id` or `--topic-id` to edit its destination, `--clear-topic` to remove a topic, or `--label` to rename the project label.
   - Run `--dry-run --json`. If a shared destination blocks the preview, retry with `--allow-shared-route` only alongside `--dry-run`.
   - Supplement the preview with a local TOML parser that emits only the relevant fields: the project's old label, the selected route's current destination, and the project and Watch profile keys affected by destination edits or reassignment. A Watch profile uses its explicit `reply_route` or inherits its project's route; project reassignment affects its inheriting profiles too. Never dump the config or token fields. When selecting and editing a route together, distinguish the original project's destination from the selected route's old destination.
   - Show what changes and who is affected; wait for confirmation. Recheck the preview and impact before applying; if they changed, ask again. Use `--allow-shared-route` on a write only after approval of the shared impact. If the CLI cannot make the requested edit, say what is unsupported and ask before editing TOML directly.
4. After an authorized write, run `doctor --config <path> --project <key> --json`. For diagnosis only, call `doctor` directly. In both cases use `--offline` when network access is out of scope. Summarize what changed and whether verification passed. Diagnose failures without retrying writes blindly. Capture and Watch remain opt-in. Sending a test message, starting a listener, or restarting a service requires its own request.
